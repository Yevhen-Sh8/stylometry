# Інтеграція DIMS з ІАС як окремого сервісу

> Документ для розробників і адміністраторів ІАС підтримки прийняття рішень,
> до складу якої входить модуль моніторингу інформаційного простору. Описує,
> як сервіс DIMS читає дані модуля моніторингу, оцінює інформаційні події за
> удосконаленою методикою та сповіщає про ознаки скоординованих інформаційних
> атак. Машинна специфікація API — `docs/openapi_v1.yaml`.

---

## 1. Архітектура

```
 ┌──────────────── ІАС ────────────────┐        ┌──────────── DIMS-сервіс ────────────┐
 │ Модуль моніторингу (збір: Telegram, │        │ dims-scanner (кожні N хв)           │
 │ YouTube, TikTok, X, Facebook,       │ SELECT │  1. змінені події з :since          │
 │ Google News…) → БД матеріалів ──────┼───────►│  2. матеріали події                 │
 │ (групування в події)                │ (read- │  3. оцінка DIMS → сповіщення        │
 │                                     │  only) │                                     │
 │ Модуль/черга сповіщень ◄────────────┼────────┤  webhook (POST JSON)                │
 │ АРМ аналітика ─────────────────────►├───────►│ dims-api: /api/v1/alerts, /review,  │
 │                                     │  REST  │           /assess, /status          │
 └─────────────────────────────────────┘        └─────────────────────────────────────┘
```

- **Напрям даних:** DIMS сам опитує БД модуля моніторингу (лише читання).
  Зміни в ІАС не потрібні, окрім облікового запису БД з правом `SELECT`.
- **Результати:** зберігаються у власному сховищі DIMS (SQLite на томі
  `dims-data`) і віддаються через webhook (push) та/або `GET /api/v1/alerts`
  (pull). **Тексти матеріалів DIMS не зберігає** — лише результати оцінки.
- **Розгортання:** Docker на серверах замовника (`deploy/ias/`), два процеси з
  одного образу: `dims-api` і `dims-scanner`.

## 2. Що робить сервіс з кожною подією

1. **Дедуплікація.** Точні (SHA-256) і майже-дублікати (SimHash, відстань
   Геммінга ≤ 10) об'єднуються в кластери копій. Копії не потрапляють до
   стилометрії (інакше Δ ≈ 0 штучно завищує $I_{coord}$), але кластер, який
   поширили кілька різних джерел, фіксується як окрема ознака координації.
2. **Агрегація за джерелом.** Матеріали одного каналу / акаунта / домену
   об'єднуються в один документ — методична рекомендація для коротких текстів
   (Δ-Burrows ненадійна на окремих постах).
3. **Оцінка DIMS** — той самий код, що й у вебзастосунку
   (`build_dims_assessment`): $R_{DIMS}$, грейд F/B/S/SS/SSS, п'ять
   індикаторів, bootstrap-інтервал і ймовірності грейдів. **Формула методики
   не змінюється.**
4. **Рішення про сповіщення** (див. розділ 4).

## 3. Підключення до БД модуля моніторингу

Схема БД ІАС сервісу невідома, тому відповідність полів задається двома
SQL-запитами (SQLAlchemy; підтримуються PostgreSQL, MySQL, MS SQL, Oracle,
SQLite — драйвер додається під час збирання образу через `EXTRA_PIP`).

| Змінна | Параметр | Обов'язкові колонки | Опційні |
|---|---|---|---|
| `DIMS_SOURCE_CHANGED_EVENTS_SQL` | `:since` (ISO-8601) | `event_id`, `updated_at` | — |
| `DIMS_SOURCE_EVENT_MATERIALS_SQL` | `:event_id` | `source`, `text` | `id`, `platform`, `domain`, `url`, `published_at` |

Приклад для PostgreSQL — у `deploy/ias/.env.example`. Рекомендації:

- Використовуйте `updated_at >= :since` (не `>`): події з тією самою позначкою
  часу не загубляться, а повторно прочитані відсіюються за відбитком складу.
- Для позначки часу використовуйте `CAST(:since AS timestamptz)`, а не `::`
  (синтаксис `::` конфліктує з іменованими параметрами).
- `source` — одиниця агрегації: ідентифікатор каналу / акаунта (для соцмереж)
  або домен (для сайтів). Для $I_{source}$ бажано передавати `domain`.
- `published_at` потрібен для $S_{time}$ (синхронність появи) і для визначення
  першоджерела в кластері копій.
- Відео (YouTube, TikTok): передавайте транскрипт / опис як `text`;
  матеріали без тексту пропускаються.
- Найкраще створити в БД ІАС **окремий view** з потрібними колонками та
  користувача лише з `SELECT` на нього.

Водяний знак (`since`) зберігається після кожного проходу. Перший прохід
охоплює `DIMS_SCAN_LOOKBACK_HOURS` (24 год). Якщо в проході сталася помилка
доступу до БД, водяний знак не просувається далі останньої успішної події.
Подію переоцінюють лише тоді, коли змінився її склад (додано або змінено
матеріал).

## 4. Правило сповіщення (провізорне)

| Тип | Умова | Обґрунтування |
|---|---|---|
| `dims` | грейд ≥ `DIMS_ALERT_MIN_GRADE` (S) **і** ≥ 1 ознака координації: $I_{coord}$ ≥ 0,40; пари з Δ < θ; ідентичний текст у ≥ 3 джерелах | Наказ № 46: S — «опрацювання + пропозиції щодо реагування» |
| `copy_paste` | ідентичний текст поширили ≥ `DIMS_ALERT_MIN_COPY_SOURCES` (3) різних джерел | Операційне доповнення до методики: після дедуплікації копії не входять у $R_{DIMS}$, тож грейд їх не відображає. Вимикається `DIMS_ALERT_COPY_PASTE_STANDALONE=0` |

Повторне сповіщення по події надсилається лише при ескалації: вищий грейд
або новий тип сповіщення. Невдала доставка webhook повторюється в наступних
проходах.

> **Усі пороги провізорні.** Їх слід відкалібрувати за даними дослідної
> експлуатації (ROC / індекс Юдена, `docs/validation_protocol_ua.md`).

## 5. Зворотний зв'язок аналітика → валідація методики

`POST /api/v1/alerts/{id}/review` з `status` (`confirmed`/`rejected`) та
`expert_grade` фіксує рішення аналітика. `GET /api/v1/feedback` віддає пари
«грейд DIMS ↔ експертний грейд». Під час дослідної експлуатації так
накопичується розмічений набір для `tools/validation.py`: зважена κ, матриця
плутанини, ROC-пороги. Для сліпої розмітки експерт має виставляти грейд до
того, як побачить оцінку DIMS.

> Обмеження: розглядаються лише події, що стали сповіщеннями. Для оцінки
> хибнонегативних результатів потрібна додаткова вибірка подій, які
> сповіщеннями не стали (`GET /api/v1/events/{id}/assessment`).

## 6. Розгортання

```bash
cp deploy/ias/.env.example deploy/ias/.env        # заповнити значення
docker compose -f deploy/ias/docker-compose.yml --env-file deploy/ias/.env up -d --build
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:5001/api/v1/status
```

Без Docker: `gunicorn app:app …` + `python -m core.ias_scanner --interval 300`
(або `--once` у cron / systemd-timer).

## 7. Безпека

- Окремі сервісні токени для кожного клієнта (`DIMS_SERVICE_TOKENS`);
  у журналах фіксується лише незворотний ідентифікатор `svc-xxxxxxxx`.
  Адмін-токен вебінтерфейсу й сервісні токени взаємно не замінні.
- API v1 без налаштованих токенів повертає 503 і не відкривається випадково.
- Адмін-токен вебінтерфейсу приймається лише в заголовку (не в URL).
- Доступ до БД ІАС — лише читання; тексти не копіюються в сховище DIMS.
- Порт за замовчуванням прив'язаний до `127.0.0.1`; зовнішній доступ —
  через reverse-proxy з TLS відомчої PKI.
- Для штатної експлуатації в ІТС МОУ потрібна КСЗІ з державною експертизою
  (Наказ МОУ № 630 від 13.09.2024). Для дослідної експлуатації варто
  погодити з підрозділом захисту інформації склад даних і мережеву взаємодію.

## 8. Відомі обмеження

1. **Валідацію методики ще не проведено** (у наборі 1 подія-приклад). Тому
   грейди й сповіщення є допоміжними: рішення ухвалює аналітик.
2. **Короткі тексти.** Агрегація за джерелом допомагає, але Δ-Burrows надійна
   від ~2 500 слів (Eder, 2015). Короткі пости дають широкий довірчий
   інтервал — сервіс додає попередження.
3. **Лексиконні індикатори** ($I_{content}$, $I_{impact}$) розпізнають лише
   маркери зі словників; перефразовану пропаганду без маркерів вони можуть
   не помітити.
4. **Змішані мови** в одній події знижують достовірність стилометрії
   (попередження в `warnings`).
5. **Сховище стану** (SQLite) розраховане на один вузол. Для кластерного
   розгортання його слід перенести на PostgreSQL ІАС.
